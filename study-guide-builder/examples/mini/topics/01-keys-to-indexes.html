Big idea

Arrays are fast at one thing: “give me element i” takes the same tiny time for any i. A hash table turns every lookup into that operation by computing, from the key alone, which index to look at.

The problem: finding things

Suppose you store student records in an unsorted list. To find ID 48213 you scan from the start until you hit it, so the work grows with the number of records n. We write that as O(n). Sorting helps (binary search is O(log n)), but can we do better, with no searching at all?

Student IDs are numbers up to 1,000,000,000 and 5,000 students are enrolled. Could you just use the ID as the array index? What would go wrong?

It would work, because lookup is instant, but you would allocate an array with a billion slots to hold 5,000 records. Almost all of it would be empty. This is called direct addressing. Hashing keeps the instant lookup but shrinks the array to a sensible size.

The trick: a hash function

A hash function h takes a key and returns an index between 0 and m−1, where m is the size of the array (the number of buckets). The simplest example for integer keys is the division method:

h(k) = k mod m
Real-life example

A coat check. You hand over your coat and get ticket #31. The attendant does not search the rack; the ticket number tells them exactly which hook to go to. The hash function is the rule that turns your coat (the key) into a hook number (the index).

What makes a good hash function?

  • Deterministic: same key, same index, every time. Otherwise you cannot find what you stored.
  • Fast: if computing h(k) is slow, you lose the benefit of indexing.
  • Uniform: keys should spread evenly over the buckets, so no bucket gets crowded.
Table size m = 7, h(k) = k mod 7. Where do the keys 10, 25, 31 and 44 go?
  1. 10: 10 = 1·7 + 3, so h(10) = 3. Store it in bucket 3.
  2. 25: 25 = 3·7 + 4, so h(25) = 4. Bucket 4 is empty, so store it there.
  3. 31: 31 = 4·7 + 3, so h(31) = 3. Bucket 3 already holds 10! This is a collision.
  4. 44: 44 = 6·7 + 2, so h(44) = 2. Bucket 2 is empty, so store it there.
  5. Takeaway: four keys, but two of them wanted the same bucket. Even a small example collides, which is why topic 2 exists.
Memory trick

“Same key, same slot.” Hashing is a chopping-and-mixing machine: put in the same ingredients and you always get the same dish, but different ingredients can sometimes give the same-looking dish (a collision).

Your table has m = 7 buckets and you insert 8 keys. Can you guarantee there are no collisions? Why or why not?

No. With 8 keys and only 7 buckets, at least two keys must share a bucket (pigeonhole principle). Even with fewer keys than buckets, an unlucky hash function can still collide, as 10 and 31 did above.
